# StructuralAI — AI-Powered Structural Health Monitoring System

StructuralAI is a full-stack platform for automated crack detection, structural health
scoring, and physics-based damage assessment of concrete/masonry structures from photographs
and structural parameters. It combines computer vision (crack detection, segmentation, and
width/depth measurement), classical machine learning (structural health index, risk, and
remaining-useful-life prediction), and original physics-based engineering models (fracture
mechanics capacity analysis and closed-loop epoxy grouting control).

## Architecture overview

```
Image upload ──► Crack detector (SwinCrackNet / CrackNet) ──► bounding boxes
             └─► U-Net segmentation ──► crack mask ──► skeletonization ──► width/depth (IS 456)
                                                                        └─► physics fracture engine (LEFM)
                                                                        └─► grouting controller (epoxy injection plan)

Structural parameters ──► XGBoost / RandomForest models ──► SHI, Risk class, RUL
                                                          └─► SHAP explainability
                                                          └─► Gemini-based narrative report + PDF
```

Two frontends talk to the same FastAPI backend: a React SPA (primary) and a legacy Streamlit
dashboard (`app.py`).

## Tech stack

- **Backend:** FastAPI, Uvicorn
- **Computer vision / deep learning:** PyTorch, Torchvision (Swin Transformer backbone), OpenCV, Albumentations
- **Classical ML:** scikit-learn, XGBoost
- **Explainability:** SHAP
- **LLM / agent:** LangChain + Google Gemini (`gemini-1.5-flash`)
- **Reporting:** ReportLab (PDF generation)
- **Frontend:** React, Axios, Recharts
- **Legacy dashboard:** Streamlit

## Setup

### Prerequisites

- Python 3.11+ (tested on 3.11 and 3.12)
- Node.js 18+ and npm (tested on Node 22)
- A Google Gemini API key (for the AI narrative report and chat features — optional; the
  agent falls back to a rule-based report if absent)

### Backend

```bash
conda create -n structural_ai python=3.11
conda activate structural_ai
pip install torch torchvision torchaudio --index-url https://download.pytorch.org/whl/cu121   # or the CPU build
pip install -r requirements.txt
```

If port 8000 is already in use on your machine, set `STRUCTURALAI_PORT` (backend) and
`REACT_APP_API_URL` (frontend), e.g. `http://127.0.0.1:8010`.

`requirements.txt` now includes `langchain-google-genai`, `python-dotenv`, `scipy` and
`scikit-image`.

Create a `.env` file in the project root:

```
GEMINI_API_KEY=your_google_gemini_api_key_here
```

### Model weights (Git LFS)

The trained weights (`models/**/*.pth`, `models/**/*.pkl`, `models/*.pt`, about 170 MB) are
stored with [Git LFS](https://git-lfs.com), so they come down with the repo. They are
tracked via `.gitattributes`; do not add them back to `.gitignore`.

**On a new machine, install Git LFS before cloning:**

```bash
git lfs install
git clone https://github.com/2005lakshya/Structural_AI.git
```

For an existing clone, run `git lfs install` then `git pull`.

**Check it worked:** `git lfs ls-files` lists the weight files, and
`models/ml/shi_regressor.pkl` should be real binary data. If the weights are tiny text files
(a few lines starting with `version https://git-lfs...`), LFS was not installed when you
cloned. Fix it with:

```bash
git lfs install
git lfs pull
```

**Adding or updating a weight file** needs no extra steps. A new `*.pth`, `*.pkl` or
`models/*.pt` is picked up automatically by the patterns in `.gitattributes`. To track a new
location or type, run `git lfs track "<pattern>"` and commit `.gitattributes`.

GitHub's free LFS quota is 1 GB of storage and 1 GB of bandwidth per month, so avoid
committing many model versions.

## Crack width measurement accuracy

`/measure_crack_width_image` locates the crack with the U-Net, then measures width at full
photo resolution (sub-pixel FWHM of the intensity profile across the crack).

- **A real scale is required for real mm values.** In the UI, click the two ends of an object
  of known length (ruler, coin, gauge scale) and enter its length. The camera-distance mode
  is only a rough guess and can be off by several times.
- **Resolution limit.** A crack narrower than about 2 px in the photo cannot be measured.
  For a typical phone photo of a 75-100 mm core (3-4 px/mm) that is about 0.5 mm. Hairline
  cracks (for example 0.04 mm from a crack gauge) need a macro photo at 100+ px/mm, or the
  gauge itself. The response includes `min_resolvable_width_mm` and `warnings`.
- **Gauge check.** Enter your gauge reading in the UI (`lab_reading_mm`) to see the
  software's error against it.
- The U-Net can also flag non-crack features (ink marks, aggregate edges, edges of the
  background). Crop the photo to the crack for best results.

## Training the models

All training scripts read from `data/` and write weights to `models/`.

```bash
python scripts/train_cracknet.py        # CrackNet CNN classifier
python scripts/train_swin_cracknet.py   # SwinCrackNet transformer classifier
python scripts/train_unet.py            # TinyUNet segmentation
python scripts/train_ml.py              # SHI / risk / RUL tabular models
python scripts/generate_tabular_data.py # regenerate synthetic tabular dataset
```

The legacy YOLOv8 pipeline (superseded by CrackNet/SwinCrackNet, no longer called from the
backend) can still be trained with `python scripts/train.py`.

## Validation and limits (read before citing any number)

**Width measurement.** `python scripts/validate_width_synthetic.py` renders cracks of known
width on a noisy texture, blurs like a camera, and measures them (output:
`outputs/width_validation.csv`). Result with this code: cracks >= 4 px wide are measured
within about 7 %; below ~2 px the estimate is dominated by optical blur (a 0.5 px crack reads
as ~2 px). This is the physical floor of any photo-based method, not a bug. It is a synthetic
benchmark; it does not replace gauge-referenced real photos.

**Real-data resolution study.** `docs/RESULTS_krkCMd.md` evaluates the width measurement on 14,198 real
crack profiles (krkCMd dataset, CC BY 4.0) re-imaged at 2.5-252 px/mm. Error is flat above ~25 px/mm
and rises steeply below ~12 px/mm; sub-pixel interpolation helps only at the coarse end; the method is
NOT more accurate than the dataset's own deep-learning benchmark. Read the "does NOT support" section.

**Hairline cracks (e.g. 0.04 mm).** At a typical 3-4 px/mm core photo, 0.04 mm is ~0.15 px
wide and cannot be measured from the image. `/measure_crack_width_ridge` reports the *apparent*
optical width and states when a supplied `gauge_reading_mm` is below the photo's resolution.
Resolving 0.04 mm needs >= 50 px/mm (macro lens or microscope) or the gauge itself.

**Segmentation.** The learned U-Net and the sliding-window detectors were trained on tightly
cropped concrete patches and fail on full-scene photos (they flag clothing, shadows, hands).
Responses now include `box_coverage_fraction` and a `warning` when boxes cover > 50 % of the
frame. For full-scene photos use `/measure_crack_width_ridge` (training-free ridge filter) with
an `roi`; mark ink/labels with `exclude` boxes. It can still pick up aggregate edges and marks.

**Risk / SHI / RUL models** are trained on 350 rows generated from a formula plus noise
(`scripts/generate_tabular_data.py`). Their accuracy shows they learned that formula, not
that they predict real buildings. The repair cost is a fixed formula. The risk model does
not recover the "Safe" class on the held-out split.

**Reported U-Net Dice (0.7345)** is the value logged at training time; it cannot be recomputed
because the segmentation dataset is not in the repo. `/model_performance` labels it as such.

**Acoustic-optical stage** (`scripts/acoustic_optical_inversion.py`) combines the measured
surface trace/widths from the photo with ONE measured UPV depth (IS 13311). It does not estimate
a depth profile or void volume (an earlier assumption-based version was removed because it was
not validated). The grouting plan only runs when you supply `void_volume_ml` yourself. The
default UPV times (`t1_us`, `t2_us`) are placeholders; enter your own readings.

## Known issues

- The image datasets listed above are not in the repository; retraining the vision models
  requires downloading them first.
- The CrackNet checkpoint is from epoch 2 (val acc 0.66); the Swin checkpoint is from the
  first head-only phase. The PI-CrackNet checkpoint (val acc 0.888) is the one used.
- `TinyUNet` is defined in three places (`backend/main.py`, `scripts/train_unet.py`,
  `scripts/extract_features.py`).
- Saved sklearn/XGBoost models were pickled with scikit-learn 1.9.0 and warn on 1.9.1;
  re-run `python scripts/train_ml.py` to regenerate them.
- Chat/LLM report needs `GEMINI_API_KEY`; the model name is set with `GEMINI_MODEL`
  (default `gemini-2.5-flash`, untested without a key). Copy `.env.example` to `.env`.
- `/api/unified_invention_pipeline` and `/api/pump/simulate_step` are API-only (not in the UI).
